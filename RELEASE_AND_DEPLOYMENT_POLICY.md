# VenQore build and deployment policy

This policy applies whenever anyone asks an IDE or agent to build, package, publish, or deploy VenQore. Read it before touching release artifacts. It remains in force for future requests.

## Current release block

**Do not upload `app-code/main-app/AMD_POS_Update_v6.0.5.zip`.** The packaged Composer autoloader fails in an isolated PHP 8.2.23 process because eight files it automatically requires are missing. The updater can also expose a partial update after extraction or migration errors. The full evidence, implementation handoff, and acceptance tests are in [UPDATER_V6.0.5_AUDIT_AND_IDE_FIX_INSTRUCTIONS.md](UPDATER_V6.0.5_AUDIT_AND_IDE_FIX_INSTRUCTIONS.md).

The exact artifact SHA-256 is `C220DB4F93625BB5537C0EB39A572740652FB35E1413BAAD6EA98912BFF694E4`. Never overwrite it or describe it as approved. Choose a new version for any repaired package.

**The later v6.0.6 candidate is also not approved for production.** Its artifact SHA-256 is `1B3D4AF3D66104EC311F054A28706FBC559241F65BC4AA4BBBFA12F02177AB98`. An independent check confirmed that its Composer autoloader loads in isolation under PHP 8.2.12, its production Composer metadata has no eager autoload references missing from the ZIP, and the recorded frontend manifest references resolve. These are package checks only; they do not approve its application behavior, migrations, web updater, or deployment.

The current 6.0.6 builder does **not** run `npm run build`, even though it generates Ziggy routes after staging frontend output. It treats failed package discovery and Ziggy generation as non-fatal, copies a possibly dirty working tree while recording only `git rev-parse HEAD`, and deletes an existing same-version ZIP before publishing its replacement. The included `release-manifest.json` is plain metadata, not signed release verification.

The current web updater source now sets its custom lock to maintenance mode before extraction, keeps normal traffic blocked through migrations/cache work, and leaves the site held for recovery on a mutation failure. Those are useful safeguards, but extraction still overwrites the active release file by file, the package is an overlay that never removes stale files, and there is no automatic code rollback. It has not been rehearsed against the live host and database. Treat it as maintenance-window-only and unapproved for the next production release until the exact candidate and recovery procedure pass staging.

**The v6.0.7 ZIP is also blocked.** Its archive is 157,389,266 bytes (150.1 MiB). Inspection found two SQLite database files under `database/` (16.2 MiB compressed) and the Windows Station installer under `public/downloads/` (73.8 MiB compressed). The workspace `.env` selects MySQL, and `config/database.php` defaults to MySQL; these SQLite files are bundled baggage, not the configured database. The builder copies all of `database/` and `public/`, but its `*.sqlite*` cleanup checks only the staging root, so it misses `database/database.sqlite` and `database/clean.sqlite`. The installer is a separately distributable product download, not a dependency of the POS web runtime; because the app links to it, a clean-install procedure must preserve or relocate that download separately before omitting it from the update ZIP. The archive also contains frontend test sources and Composer package test/readme files. The app download metadata also advertised the SHA-256 of an empty file, so it was not a valid installer checksum. Do not upload v6.0.7 or use it as a clean-install bundle.

The new SSH scripts are not production-approved. `deploy_production.sh` runs database migrations against the live shared database before activation, and its health-triggered rollback switches code only; it does not reverse migrations. Compatibility and data effects for the exact target have not been rehearsed. `deploy/bootstrap_atomic.sh` moves the existing application directory aside and installs the symlink layout before asking the operator to change the webroot and reload Nginx. The supplied instructions to run it first could interrupt the live site; the host/webserver topology and permissions are not verified. **Do not run the 6.0.6 web updater or the supplied bootstrap/deploy commands on production.**

## Every future build request

Read `SERVER_FILE_KEEP_DELETE_GUIDE.md` for persistent user preferences and the actual screenshot-based keep/delete classification. The canonical builder invokes `release-package-boundary.ps1` after frontend compilation and validates the extracted candidate again. Old V6 HTML/design exports, frontend tests, development configuration and local public uploads are excluded; `public/v6/assets` remains required by current React pages. Do not delete all V6 assets or all Markdown/spreadsheet files by extension. Do not present the updater ZIP as a replacement for the domain's hosting entrypoints or preserved runtime state.

Do not immediately create a ZIP. First identify whether the request is for a fresh install, a self-hosted update, or the SaaS production release; inspect the intended source branch/commit and local changes; ask for the target version if it was not supplied; and inspect the actual live version/environment before claiming an upgrade is compatible.

Use a dedicated, repeatable builder that stages a clean release. Install PHP dependencies from `composer.lock` inside staging using production mode. Never copy a development `vendor/` tree and delete selected directories afterward. Generate route inputs before compiling frontend assets. Build frontend output from the same source revision as the backend. Exclude secrets, runtime state, uploads, sessions, database files (including every `*.sqlite*` file under `database/`), logs, and local caches. The application currently uses MySQL in the live `.env`, and its config default is MySQL; a release must not include a SQLite database file. Keep the SQLite connection definition only if local tests need it; that does not justify shipping a SQLite data file.

Treat the web-updater ZIP as an overlay: it replaces files named in the archive and does not delete unrelated files already on the server. Define and validate a strict package inventory, and enforce the 120,000,000-byte upload ceiling before publishing. Keep large separately distributed assets such as the Windows installer outside the updater ZIP and publish them through a separately verified asset path. The builder records external asset paths, sizes, and SHA-256 hashes; upload the installer manually only when it changes or when restoring a clean installation. If creating a clean-install bundle, label it separately and include a rehearsed procedure for the webroot, `.env`, uploads, storage, installer download, permissions, and rollback. Never instruct an operator to clear `public_html` based only on an updater ZIP; first identify the Laravel base path and actual document root and preserve all persistent state.

Treat artifact creation as a gated process. Validate the final archive itself: expected layout and version, complete files, archive readability and safe paths, Composer autoload in an isolated clean extraction, PHP/platform requirements, Laravel boot and package discovery, every frontend manifest reference, and checksums. Validate the final dependency tree and metadata together. A successful source checkout, a ZIP existing, or a green Vite build alone never means the package is safe to release.

Compare migrations with the exact live migration ledger and rehearse them against a protected staging copy with production-like data. Inspect modified historical migration files: installations that already recorded them will not rerun their changed code. Use new forward repair migrations where needed. Review uniqueness/data conflicts, table locks, downgrade compatibility, and backups that have been restored in a rehearsal. Keep financial backfills and demo reseeding out of the normal deployment path; review and run them as separate, tenant-scoped operations when explicitly required.

Give every build one of these explicit outcomes: `artifact validated for staging`, `blocked` with evidence, or `approved for the named target after staging`. Do not use `production-ready` or direct a live upload until the exact final artifact passes the release gates and the precise live-to-target upgrade passes staging.

Persist the artifact hash, source revision, composer/npm lock hashes, builder version, build commands, validation results, target version range, migration review, and recovery procedure beside each release. Never silently overwrite a prior release ZIP.

## Deployment choice for this project

For production, use SSH as the deployment channel, with an audited server-side release procedure. SSH alone does not prevent downtime or data loss.

The in-app web updater is disabled by default (`VQ_WEB_UPDATER=false`) and is not the recommended production release mechanism. Its current implementation writes files into the active application and blocks normal customer requests while an update lock exists. Its failure and concurrency handling must be repaired before recommending it for any production update.

Do not run the existing `app-code/main-app/deploy.sh`, `app-code/main-app/deploy_production.sh`, or the release ZIP scripts as an approved shortcut. They have not passed this release audit. In particular, the SSH deploy script installs dependencies/builds in the live checkout before maintenance and has no code rollback; the production deployment script uses a two-move directory replacement rather than a single atomic activation, migrates after the replacement, and has no effective rollback trap after swap. Their comments overstate their atomicity/recovery guarantees.

Implement and rehearse an immutable release-directory deployment with shared protected runtime state and a single atomic active-release switch. Run compatible, additive database changes before activation; hold old/new code compatibility through the switch; check web health in a fresh process; and verify queue, scheduler, and other enabled workers. Keep the previous release available. If the host cannot support a safe atomic switch and compatible migrations, state that the proposed approach requires maintenance time and provide the measured window instead of promising zero downtime.

For the first repaired production release, account for the currently installed updater/deployment code: fixes delivered inside a ZIP are not active during the first extraction. Validate and rehearse an SSH/bootstrap deployment path that does not depend on the old in-app updater to make itself safe. Do not run the live updater with 6.0.5.
