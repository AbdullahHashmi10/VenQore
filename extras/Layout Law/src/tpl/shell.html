The sidebar question has an arithmetic answer

You asked: when someone opens the sidebar on a 1280 screen, do the cards rearrange, or do we overlay it with a higher z-index — and where is the sweet spot? It is not a taste question. Pushing is always nicer: the page stays fully usable, nothing hides behind a scrim, there is no modal trap. So the rule is push whenever pushing does not damage the grid — and pushing damages the grid the moment the content can no longer sustain the narrowest desktop the law already ships.

1216px

The push threshold. Below it the nav overlays; at or above it, it pushes. 1216 = 264 + 48 + 904 — the sidebar, the two page margins, and 904px, which is the content width at the 1024 rail. That is the narrowest desktop grid in production today: 8 columns at exactly 92px. Expanding the nav may cost you cards per row. It may never cost you the grid.

Where the divider is allowed to stop

The splitter is not a free-for-all with a guard rail bolted on. Its travel is the No-Regression Rule: max = vw − 2·margin − contentFloor. On a dashboard the content floor is the same 904px that gives us 1216, so the handle physically cannot be dragged into breaking the grid. Below the push threshold the nav overlays and costs the content nothing, so there the stop is instead the widest sidebar the narrowest pushing screen can carry — which is 264px, the default, arrived at from the other direction.

264 was never a taste call. At a 1920 viewport, 1920 − 48 − 264 = 1608 = 12×112 + 11×24. The default sidebar is exactly the width that yields twelve columns at exactly the 112px target. The splitter is magnetic at every width with that property, for every legal column count — so as you drag, the grid snaps through 12, 10 and 8 columns at their most regular, and the readout tells you which one you are on.

Flow and Free

Packing left is not a bug, it is one of two legitimate answers — and every mature editor ships both under some name. Gridstack calls it float versus gravity; react-grid-layout v2 made compaction pluggable and named the other one noCompactor, “free positioning”; Grafana ships it to end users as Auto grid versus Custom layout. So it is a user setting here too, not an implementation detail.

The hard part: a layout authored at 24 columns has to be legal at 4

Flow dodged this by never storing a position — nothing stored, nothing to be wrong. Free has to store one, so Free needs a projection, and the law takes the same one Gridstack ships as moveScale: “scale and move items by the ratio of newColumnCount / oldColumnCount.” Width and column scale by N′/N, the row is absolute, and collisions settle downward only. Then two rules that are ours:

  • Always project from an authored class, never from a projection. round() is lossy, so chaining 24→20→16→12 drifts — which is exactly the complaint in react-grid-layout issue #1663, that a layout does not pop back when the window grows again. One hop, ever. Returning to the class you authored in restores it exactly.
  • The ratio does not know what is in the box. A metric card scaled 24→8 lands one column wide, and one column holds no fit at all. So every projected box is clamped back into its category's own travel — the same travel the resize handle uses — before it settles.
At four columns Free is not offered at all: the leanest card the law can make is two columns, half the grid, so a “gap” there is one card's worth of damage rather than composition. Dynamics 365 Commerce draws the same line, dropping drag-and-drop entirely below 1024×768. Your boxes are kept, sorted row-major into reading order, and restored the moment the grid can carry them again.

Where the resize handle stops

The handle's travel is the category's fit list read backwards. resolveCard asks “how wide must the box be for this fit”; a resize handle asks “what is the best thing I can put in this box”. Same ordered fits, same measured floors, so the two readings can never disagree — and the solver asserts it at every breakpoint.

Sticky intent. On a push-capable screen the hamburger sets a preference, not a temporary state. Expand it at 1920, shrink the window past 1216 and the nav demotes to a rail on its own; grow it back and your choice returns. The nav is never forgotten, and it is never forced.

Every width, both directions

The one column that matters is the last one. An automatic reflow — one the user did not ask for — is a jolt. A reflow that happens because they pressed the hamburger is feedback. So the only rows where the grid reflows are the ones where the user asked.

The nav is not the same on every screen

Solving the invoice editor turned up a cliff at the most common laptop transition: at 1265 the nav is a rail and the line table gets 807px — seven columns. At 1280 the nav becomes the 264px sidebar, the table drops to 680px, and the same invoice loses a column on a bigger screen. You navigate from a dashboard or a list, so the nav is part of the task there. You do not navigate from an invoice or a register: there it is parked chrome, and 192px of parked chrome is a whole table column.

Six card categories

A category is not a size. It is an ordered list of fits, each with a pixel floor measured from real advance widths — Space Grotesk 600 tabular digit = 0.620em, read out of the font binary. A card starts at the fit its author designed. If the column is narrow it gets wider; only when widening is exhausted does it degrade to a leaner fit, which trades a column for a row and re-lays its inside.

Edit mode

Edit mode changes what the user may change, never what the law allows: every gesture is snapped before it commits, so a user cannot save a layout the law would reject. This is also the contract Reckoner will drive — it emits card descriptors, never a layout, and the engine turns descriptors into geometry.
