# STEP 4 — Billing simplification

## ⚠️ The plan's instruction for this step is dangerous as written

It says: *"Delete feature booleans from `config/plans.php` and `PlanFeatureMatrixSeeder`."*

**Doing literally that would take every gated feature away from every customer at once.** Three reasons, each verified in your repository on 15 August:

**1. `config/plans.php` is not the runtime source of truth.** Its own header says so:

> *"The runtime source of truth is the `plan_limits` TABLE, written by `PlanFeatureMatrixSeeder` and read through `PlanRepository` → `Tenant::getLimit()` → `PlanGate`."*

Editing the config changes nothing for an existing tenant.

**2. Deleting keys from the seeder does not delete rows already in the table.** Existing tenants keep their seeded `false` rows forever.

**3. And if you did delete those rows, the gate fails closed.** `PlanRepository::canUseFeature()`:

```php
$val = self::getEffectiveLimit($tenant->id, $tenant->plan ?? 'starter', $feature);

if ($val === null) {
    return false; // Default deny per T2-2
}
```

**A missing key is a denied feature.** So "delete the booleans" would 403 every gated route for every customer on every plan — the exact opposite of "every module, every plan".

## What to do instead

`2026_08_16_000300_include_every_module_on_every_plan.php` **sets** every module-owned key to `'1'` on every plan.

Same outcome, reached by writing truth into the table the gate actually reads rather than removing rows it interprets as "no". Nothing about `PlanGate`, `PlanRepository`, the 132 route middlewares or the entitlement suite has to change — which turns the riskiest change in the project into a reversible `UPDATE`.

**43 keys become free.** Sourced from the `legacy_gate` field of all 46 modules, **plus the aliases `canUseFeature()` resolves internally** — `compositions → bill_of_materials`, `stock_valuation → report_stock_valuation`, `aged_receivables → report_sales_aging` and others. Miss one of those and a module stays gated by a key nobody remembered existed.

**Verified:** every `legacy_gate` in the registry is covered, and `NOW_FREE` and `KEEP` do not overlap.

## What is deliberately untouched

**The four meters** — `transactions_per_month`, `staff_limit`, `locations`, `sku_limit`. This is what customers actually pay for.

**The four honest exceptions** — `growth_engine` (AI costs money per call), `woocommerce` (per-connection infrastructure), `api_access` (enterprise buyer), `ltd`/`hosted_until` (lifecycle, not a feature).

Also untouched: `reports`, which is a **string** (`'basic'`/`'advanced'`), not a boolean. Flipping it to `'1'` would silently downgrade every advanced report.

## The `growth_engine` bug is fixed in the same migration

`config/plans.php` line ~175 has `'growth_engine' => true` on `ltd_2`, and `PlanTruthFailClosedTest` is failing because of it. **Metered AI, given free and forever to buyers who paid once.** The migration sets it to `'0'` on all three LTD tiers. Subscription tiers keep theirs — those customers pay monthly, so an included allowance is honest there.

## Order of operations

```bash
mysqldump venqore plan_limits > plan_limits_before_step4.sql   # 4 seconds. Do it.
php artisan tinker --execute="require 'tools/verify_step4.php';" > step4_before.txt
php artisan migrate
php artisan tinker --execute="require 'tools/verify_step4.php';" > step4_after.txt
diff step4_before.txt step4_after.txt
php artisan test
```

`verify_step4.php` prints a plan × feature grid. After the migration **every module row must read `yes` on every plan**, the four meters must be unchanged, and `growth_engine` must be `no` on all three LTD tiers.

If a module is still denied, it is almost certainly an alias — check `canUseFeature()`'s `$aliases` map and add the resolved name to `NOW_FREE`.

**Then, and only then**, at your leisure and in separate commits: remove the `plan.feature:` middlewares from `routes/web.php`; later still, delete the keys entirely. Three small reversible steps beat one large irreversible one.

## Update the config file too

`config/plans.php` is only a fallback, but a fallback that disagrees with the table is a trap for whoever reads it next. After the migration, set the same 43 keys to `true` across all seven plans, set `growth_engine => false` on `ltd_1/2/3`, and update the header comment to say Step 4 changed the model.

Same for `PlanFeatureMatrixSeeder` — a fresh install must land in the same state a migrated one does, or your dev machines diverge from production and you debug the difference for a day.

# STEP 14 — Migration rehearsal

## The criterion

> **"Restore a production-shaped DB copy, run the backfill, diff nav/routes/permissions/reports before vs after."**

`tools/tenant_snapshot.php` does the diffing.

```bash
# 1. Restore a copy of production. NEVER rehearse on production.
mysql -e "CREATE DATABASE venqore_rehearsal"
mysql venqore_rehearsal < production_dump.sql

# 2. Point .env.rehearsal at it, then snapshot the world as it is
php artisan tinker --env=rehearsal --execute="require 'tools/tenant_snapshot.php';" > before.json

# 3. Everything: tenant_modules + backfill, service tables, config versions, Step 4
php artisan migrate --env=rehearsal

# 4. Snapshot again
php artisan tinker --env=rehearsal --execute="require 'tools/tenant_snapshot.php';" > after.json

# 5. The moment of truth
diff before.json after.json
```

## Reading the diff

| Section | Expected | If it moved |
|---|---|---|
| `nav` | **identical** | a customer lost or gained a menu item — stop |
| `reachable` | **identical** | a route changed reachability — the backfill missed a tenant |
| `reports` | **identical** | check `ReportModuleMap` against the tenant's modules |
| `row_counts` | **identical** | 🚨 **STOP THE LAUNCH.** A configuration migration must never touch business data |
| `ledger_balance` | **identical, and 0.00** | 🚨 stop immediately |
| `meters` | **identical** | Step 4 touched something it should not have |
| `features` | **changes expected** | every change must be `false → true`. **A single `true → false` is a customer losing something** |

**A non-empty diff is not necessarily a failure — but it is always a decision.** Read every changed line and be able to say why. *"It's probably fine"* is how a customer loses a menu item on launch day.

## Why a snapshot rather than a test

A test proves the code behaves on fixtures you wrote. This proves it behaves on **your actual customers' actual data** — the tenant with 40,000 products and a plan override nobody remembers creating. Those are the ones that break, and they cannot be fixtured because nobody knows they are odd.

## Five manual walkthroughs, each with a real transaction

Automated tests will not catch "this feels broken". Do these by hand on the rehearsal database:

| # | Preset | Do this | Must be true |
|---|---|---|---|
| 1 | **Simple Counter** | scan, sell, take cash, print | 2 nav items. Feels like a product, not a demo |
| 2 | **Cafe** | sell a made item | ingredients left stock, COGS is right, ledger balances |
| 3 | **Retail Shop** | sell on khata, take partial payment | receivable appears, statement is right |
| 4 | **Restaurant** | seat a table, fire a kitchen ticket, settle | table frees up, sale posts |
| 5 | **Wholesale** | quote → order → invoice → payment | every document links, ledger balances |

Then the one that matters most:

**6. Switch a module off and type its URL.** It must 403 to the builder, not 500 and not load.

**7. The "it was recording all along" screen.** Turn Inventory on for a tenant that has been selling without it. If it says *"VenQore has been tracking this since March"* with real numbers, that is your demo video's best ten seconds.

## Rollback plan, written before you need it

```bash
php artisan migrate:rollback --step=4      # config versions, services, plans, tenant_modules
mysql venqore < plan_limits_before_step4.sql
php artisan cache:clear
```

Every rollback path in this project gives customers **more** of their software, never less: no `tenant_modules` rows → `ModuleService` fails open → everyone has everything. Preserve that property if you change anything.

# STEP 15 — Launch kit

## The changelog to existing customers

Send this before the listing goes live, not after. Existing customers finding out from a marketplace page is how goodwill evaporates.

> **Every VenQore module is now included in every plan.**
>
> Nothing was taken away — a lot was added. You now pay only for how much you use, not for which features you're allowed to touch.
>
> Your plan still sets your limits: transactions per month, staff accounts, locations and products. Everything else — Manufacturing, Multi-Location, Purchase Orders, Recurring Invoices, E-Invoicing, Bank Reconciliation, every report — is yours, on every plan, starting today.
>
> Nothing about your account changes unless you want it to.

**That last line is the important one.** Every existing tenant is backfilled with everything visible; nobody has to do anything.

## The listing

**Lead with the modules and the pricing. Support with the AI.** "AI ERP builder" is a crowded claim in 2026. "Every feature on every plan, on one verified engine" is not, and it cannot be copied without rebuilding both the pricing and the engine.

> ## VenQore
> ### One Qore. Your modules. Your system.
>
> **Every business runs on the same verified engine. You add only the parts you actually need — from 46 modules, or just describe your business and let AI assemble it.**
>
> **Every module is included on every plan. You pay for how much you use, never for which features you're allowed to touch.**

Three claims, each verifiable in under a minute:

| Claim | Verified by |
|---|---|
| "Every module, every plan" | your pricing page — and every competitor's page proves it by contrast |
| "Describe your business, get your system in two minutes" | the demo video |
| "One engine, always correct" | the Qore, the test suite, and the module-added-later moment |

**Show the supported business types openly.** Fifteen visible cards. A visitor who finds theirs converts immediately; one who does not gets *"Don't see your business? Tell us — we'll build it."* That converts your biggest limitation into your best market research, and it feeds the same demand log as the AI's `unsupported` field.

## What never to say

| ❌ Never | ✅ Instead |
|---|---|
| "AI writes custom software for you" | "AI assembles your system from modules we've already built and tested" |
| "Works for any business" | "Built for these 15 business types — don't see yours? Tell us" |
| "265 features" | "46 modules, and the AI picks the right ones" |
| "AI-powered modular ERP with 46 configurable modules" | "Describe your business. Get the system that fits it. In two minutes." |

**The testing is the selling point.** "We already built and tested these" is a stronger claim in 2026 than "our AI generates it" — buyers have been burned by the second one and can verify the first.

Also, stop saying a feature count at all. Your own catalog has duplicate numbers (`#72` is used twice, `#93` twice, and six deliberate duplicates), which inflates "265" by about six. **46 modules** is a number you can defend line by line.
