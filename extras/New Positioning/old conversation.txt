# Our fundamental insight

We asked:

> **Are these actually different software problems?**

After reducing the 65-business/vertical concept, the answer is largely **no**.

A restaurant, school, hospital, software company, retailer, construction company, law firm, logistics company, etc. use different terminology, but underneath they repeatedly deal with the same fundamental concepts.

The exact number of primitives can be debated, but our current working architecture is based around:

### Universal business primitives

1. **Party** — who exists
2. **Resource** — what exists / what has value
3. **Event** — what happened
4. **Relationship** — how things are connected
5. **State** — what is currently true
6. **Rule** — what should happen under particular conditions

Then reusable capabilities sit above these primitives:

* Workflow
* Documents
* Scheduling
* Communication
* Accounting/Ledgers
* Reporting
* Automation
* Integrations
* Permissions
* Search
* Notifications
* etc.

And above that is the **industry vocabulary**.

---

# The key concept

The same underlying system can become different software simply through configuration.

For example:

| Universal concept | Retail          | School            | Hospital          |
| ----------------- | --------------- | ----------------- | ----------------- |
| Party             | Customer        | Student           | Patient           |
| Resource          | Product         | Course/Classroom  | Medicine/Bed      |
| Event             | Sale            | Enrollment        | Admission         |
| State             | Delivered       | Enrolled          | In Treatment      |
| Rule              | Tax/discount    | Grading policy    | Treatment policy  |
| Workflow          | Order lifecycle | Student lifecycle | Patient lifecycle |

The underlying platform doesn't need to become a completely different application.

The **language, fields, rules, workflows, relationships and UI** change.

That is the fundamental idea.
