# V3 Transition Blueprint & Forensic Reconciliation Guide

This document defines the comprehensive master plan to migrate the POS system entirely to the V3 architecture. This is a pure design, analysis, and planning document with no code changes executed.

---

## 1. The Core Architectural Gap: Webhook Sync vs. POS Checkout

Our forensic audit reveals a critical system vulnerability: **the system currently has two completely different inventory and accounting pipelines running simultaneously.**

### Pipeline A: In-Store POS checkout (V3 Engined)
- **Inventory:** Deducted using `FifoService` from `inventory_batches` with indexed records.
- **Accounting:** Generates double-entry journal items (`debit` to Cash/Accounts Receivable, `credit` to Sales Revenue & Cost of Goods Sold) inside `journal_items` and `journal_entries` tables.

### Pipeline B: WooCommerce Webhook Sync (Legacy V1 Engined)
- **Inventory:** Deducts stock using the legacy `InventoryService` from the old `stocks` table via `deductFromBatches()`.
- **Accounting:** Inserts a raw record into the legacy `transactions` table (which is ignored by V3 Trial Balance and P&L reports). 
- **Consequence:** Synced orders cause immediate inventory imbalances (since V3 reports query `inventory_batches`) and make the Trial Balance drift because no V3 journal entries are created for WooCommerce sales.

---

## 2. Porting Strategy for Missing Features

To transition the legacy routes, the following features inside legacy controllers must be rebuilt within the V3 Services/Controllers layer:

### A. SaleController Feature Porting
1. **Parked Sales (`parkBill()`, `recall()`, `deleteParked()`):**
   - **Legacy:** Saves a JSON blob of items in the `parked_sales` table.
   - **V3 Target:** Can use the same database structure, but when a parked sale is recalled and posted, it must go through `SaleService::post()` to generate correct FIFO batch deductions and ledger transactions.
2. **Receipt Printing (`printReceipt()`):**
   - **Legacy:** Returns a custom HTML layout with static fields.
   - **V3 Target:** Needs to load details from V3 journal items and `inventory_batches` data to show correct VAT and gross totals.

### B. WooCommerce Sync Integration Porting
1. **Legacy Webhook Processing:**
   ```php
   // Legacy WooCommerceController.php Line 106:
   $total = $this->inventoryService->processSale($itemsToProcess, $party->id);
   ```
2. **V3 Transition Rewrite Plan:**
   - Map WooCommerce payload lines to the V3 `SaleService::post()` structure:
     ```php
     $payload = [
         'customer_id'     => $party->id,
         'warehouse_id'    => $defaultWarehouseId,
         'sale_date'       => now()->toDateTimeString(),
         'payment_method'  => 'credit', // WooCommerce orders usually represent pre-paid or COD receivables
         'amount_received' => $orderTotal,
         'items'           => [
             [
                 'product_id'  => $productId,
                 'qty'         => $qty,
                 'sale_uom'    => 'PCS',
                 'unit_price'  => $price,
                 'tax_rate'    => $taxRate
             ]
         ]
     ];
     app(\App\Services\V3\SaleService::class)->post($payload);
     ```

# III. KEY MOBILE RESPONSIVENESS REFITTING PATTERNS

Every component listed above must scale smoothly using these core design systems:

```mermaid
graph TD
    A[Grid Adaptations] --> B[Single column stacked forms on Mobile]
    A --> C[Swipeable tabs for side-by-side components]
    D[Table Adaptations] --> E[Responsive Card-View swaps for rows]
    D --> F[Scrollable container boundaries with horizontal scroll indicators]
    G[Control Bars] --> H[Floating action buttons and sticky bottom bars]
```

### 1. The Dynamic Grid Stacking Pattern
Never write absolute widths on container nodes. Ensure standard grids use dynamic responsiveness:
```jsx
// Correct layout grid
<div className="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-6">
   {items.map(item => <ItemCard key={item.id} data={item} />)}
</div>
```

### 2. Table to Card Layout Swapper
For screens `< 768px`, replace tables with card lists:
```jsx
{/* Desktop View */}
<table className="hidden md:table w-full">
   <thead>{/* headers */}</thead>
   <tbody>{/* rows */}</tbody>
</table>

{/* Mobile View */}
<div className="block md:hidden space-y-4">
   {rows.map(row => (
      <div className="bg-slate-900 border border-slate-800 rounded-2xl p-4 shadow-sm" key={row.id}>
         {/* Render Row fields as key-value pairs */}
      </div>
   ))}
</div>
```

### 3. Floating Bottom Sheets for Action Items
On mobile, action triggers placed at the top (like export, filter, edit columns) must be moved into a bottom action sheet or sticky footer:
```jsx
<div className="fixed bottom-0 left-0 right-0 p-4 bg-slate-900 border-t border-slate-800 flex justify-around md:relative md:bg-transparent md:border-none">
   <button className="px-6 py-3 bg-indigo-600 rounded-xl font-bold">Apply Filters</button>
</div>
```
Given where you are — primary breadwinner now, deadline pressure, and a genuinely working hybrid system — the worst thing you could do right now is start the full 10-15 day V3 migration described in that first analysis. That's a *post-launch hardening project*, not a pre-launch one. What you actually have is one specific landmine (the WooCommerce/accounting split) and one enormous but mostly non-blocking task (254 views for mobile). Here's how I'd sequence this.

**Step 1 — Decide what "live" actually means for week one.** This changes everything downstream. Is launch = AMD Outlets plus maybe 1-2 early SaaS signups using core POS/Sales/Purchases? Or does it include WooCommerce sync being active for a real store from day one? If Woo sync isn't going to be turned on for your first real users immediately, the entire "Pipeline A vs Pipeline B" landmine in document 2 becomes a fast-follow item, not a blocker — you just keep the Woo sync toggle off in settings until it's fixed. If it *is* needed day one (e.g., AMD Outlets already has live Woo orders flowing in), it becomes P0.

**Step 2 — The one financial-integrity fix that actually matters (1-2 days, only if Woo sync is active at launch).** The fix isn't "migrate everything" — it's narrowly: rewrite the `WooCommerceController` webhook handler so that instead of calling the legacy `InventoryService::processSale()`, it builds the payload structure shown in document 2 and calls `V3\SaleService::post()`. That's it. One controller, one entry point. This brings Woo orders into `inventory_batches` and `journal_entries`, which closes the trial-balance drift. Everything else in the legacy controllers (POS, Purchases) is already hot-swapped to V3 per document 1, so this single change brings the *last* unintegrated pipeline into line.

**Step 3 — A real reconciliation smoke test, not a full audit (half a day).** Before flipping the switch, run one full business day's worth of transactions through AMD Outlets (your live install): a few sales, a purchase, a return, and — if Step 2 applies — a synced Woo order. Then check: does `SUM(debits) = SUM(credits)` in `journal_entries`, and do `inventory_batches` quantities match a physical/expected count? This is the cheap version of the "Parallel Run Auditing" idea from document 2, scoped to one store and one day instead of a 2-3 week project. If it balances, you're financially safe to go live on the hybrid architecture as-is.

**Step 4 — Mobile responsiveness: triage 254 down to ~30.** Almost nobody needs Reports #1-43, the SuperAdmin panel, the V3 next-gen admin screens, or the 60-view support/logs section to be perfect on a phone for launch — those are desktop tools you and maybe one accountant touch. What *does* need to work on a phone for a new signup: Auth/Onboarding (13 views), Pricing, the POS terminal itself (all 4 POS views — this is the make-or-break screen), the Executive Owner dashboard, Cashier dashboard, and maybe the top 4-5 reports an owner checks from their phone at the end of the day (P&L, Day Book, Stock Levels, Sales Analytics). That's roughly 25-30 views — a 2-3 day pass, not a multi-week refit. Everything else goes into a "Tier 2/3" backlog you chip away at post-launch using the patterns already documented in section III of that audit (they're solid and reusable).

**Step 5 — Schedule the real V3 migration as week 2-4 work, store-by-store.** Once you're live and earning, do the 4-phase plan from document 1, but apply it incrementally per-store behind feature flags rather than as one big-bang cutover — using the "Parallel Run Auditing" verification from document 2 each time before deleting a legacy controller. This is when the 10-15 day estimate is appropriate, because by then you're not racing a launch date with real revenue depending on it.

So the realistic pre-launch critical path is: clarify launch scope (today) → Woo sync V3 rewrite if needed (1-2 days) → reconciliation smoke test (half day) → Tier 1 mobile pass (2-3 days) → go live. That's roughly 4-6 focused days instead of 3+ weeks, and it's scoped to what could actually break trust or money on day one — everything else can visibly be "coming soon" without anyone caring.

### 1. Stock Valuation Report Audit

The `StockValuation` report **only calculates current live quantities × current cost**. It answers **"what is it worth right now"** and cannot answer "what was my stock worth on a past date."

#### Implementation Details:
As seen in `app/Services/FinancialReportingService.php` at `getInventoryValuationReport()` ([FinancialReportingService.php: L432-L470](file:///e:/AMD%20POS/AMD%20POS/app/Services/FinancialReportingService.php#L432-L470)), the report queries the database directly for batches with active remaining quantities (`remaining_qty > 0`):
```php
return DB::table('products')
    ->join('inventory_batches', 'products.id', '=', 'inventory_batches.product_id')
    ...
    ->where('inventory_batches.remaining_qty', '>', 0)
    ->select(
        ...
        DB::raw('SUM(inventory_batches.remaining_qty) as total_qty'),
        DB::raw('SUM(inventory_batches.remaining_qty * inventory_batches.unit_cost) as total_cost_value')
    )
```

#### What data is needed to make historical valuation possible?
To calculate the inventory value as of a past date `T`, the system needs to reconstruct the quantity in each FIFO batch as of that date. Because `inventory_batches` only stores a mutating `remaining_qty` column representing the current live state, this historical reconstruction is not possible with the current schema. 

To enable this, we need a **Batch Transaction Ledger** table (e.g. `inventory_batch_movements`) logging every single increment or decrement to a batch's stock with:
* `inventory_batch_id` (foreign key)
* `quantity` (signed decimal: negative for sales, adjustments, or purchase returns; positive for purchases, sales returns)
* `type` (sale, purchase, return, adjustment, transfer)
* `reference_type` / `reference_id` (pointing to the document item that caused the movement)
* `created_at` (timestamp of the event)

Using this ledger, the inventory value at date `T` would be computed by:
1. Finding all batches created on or before `T` (`created_at <= T`).
2. For each batch, reconstructing its historical quantity as:
   $$\text{Remaining Qty at T} = \text{original\_qty} + \sum (\text{Movements on or before T})$$
3. Summing $\text{Remaining Qty at T} \times \text{unit\_cost}$ across all those batches.

4. **[`config/plans.php`](file:///e:/AMD%20POS/AMD%20POS/config/plans.php) Fallback:** The file containing default hardcoded tier limits (e.g. `starter`, `growth`, `business`, `ltd_1`, `ltd_2`, `ltd_3`).

### 2. Enforcement Method
The backend **actively blocks** unauthorized routes and controller actions. The application does not simply rely on hiding frontend menu items. 

* **The Gatekeeper:** All checks flow through the [`PlanGate`](file:///e:/AMD%20POS/AMD%20POS/app/Services/PlanGate.php) class.

* **The Block:** If unauthorized, it throws a [`PlanLimitException`](file:///e:/AMD%20POS/AMD%20POS/app/Exceptions/PlanLimitException.php). If the request is from Inertia, it redirects back with a `plan_limit` payload; otherwise, it returns a **`403 Forbidden` JSON response**, which the React frontend Axios interceptor catches to open the global `UpgradeModal`.

  ```php
  if (!$tenant->google_refresh_token) {

  }
  ```

* **Scenario B: Upload attempt and credential/token failure**
  If a refresh token is present, the controller proceeds to call `$driveService->uploadBackup($tenant, $filename, $payload)`.
  1. Inside `uploadBackup`, the service attempts to get a fresh access token from Google:
     ```php
     $response = Http::asForm()->post('https://oauth2.googleapis.com/token', [ ... ]);
     ```
  2. If the API credentials or refresh token are invalid, the token refresh fails, which logs the detailed response and returns `null`.
  3. `uploadBackup` checks for `!$accessToken` and returns `false`.
  4. The controller intercepts the failure and redirects back with a **visible error banner**:
     ```php
     return back()->with('error', 'Failed to upload backup to Google Drive. Check connection logs.');
     ```
  
* **Scenario C: Code/Exception Failure**
  If an exception is encountered (e.g. database error, file systems, connectivity), the controller catches it and displays a **visible error banner** containing the exception details:
  ```php
  catch (\Exception $e) {
      Log::error("Manual Google Drive sync failed for store {$tenant->id}: " . $e->getMessage());
      return back()->with('error', 'Failed to sync backup to Google Drive: ' . $e->getMessage());
  }
  ```
